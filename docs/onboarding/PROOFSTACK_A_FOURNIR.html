SasPay — encaisser réellement

À faire d’abord en SANDBOX, puis en LIVE après un paiement de test validé.
Ce que tu dois obtenir

SASPAY_API_KEY
Clé secrète sk_test_… pour tester, puis sk_live_… pour la production. Elle n’est affichée qu’une seule fois à la création.

SASPAY_WEBHOOK_SECRET
Secret de signature du webhook. Affiché une seule fois à la création, ou après une rotation depuis le tableau de bord.

Ce qui doit être prêt côté SasPay

Compte marchand vérifié (KYC) : identité, selfie, et si tu es une entreprise, pièces d’enregistrement et fiscales demandées par SasPay.

Moyens d’encaissement : pays et réseaux mobile money / carte que tu veux activer. Le KYC doit être validé avant de pouvoir encaisser.

Comment les obtenir

  1. Va sur app.saspay.me, crée ton compte, vérifie ton email, puis crée ton marchand (« boutique »).
  2. Dépose le dossier KYC demandé et attends la validation. Sans KYC validé, le marchand reste inactif.
  3. Dans le tableau de bord, section Développeur → Clés API, crée une clé SANDBOX avec le scope PAYIN (ou BOTH seulement si tu utilises aussi les retraits). Copie immédiatement le secret complet.
  4. Toujours dans le tableau de bord, ouvre Webhooks et crée un point de réception avec exactement cette URL :
    https://proofcore-api.laudesmassamba1.workers.dev/api/webhooks/saspay
    Choisis le même environnement que la clé (SANDBOX ou LIVE).
  5. Abonne ce webhook au minimum à transaction.success. Tu peux aussi ajouter transaction.failed et transaction.cancelled pour suivre les échecs. Copie le signing secret affiché à la création.
  6. Fais un paiement de test avec la clé sk_test_…. La commande doit revenir SUCCESS côté SasPay et l’accès ne doit être activé qu’après la vérification serveur. Ensuite seulement, crée la clé sk_live_….
Ne me colle pas la clé dans le chat. La clé complète donne accès à ton compte marchand. Utilise le gestionnaire de secrets ou les commandes ci-dessous, qui n’affichent pas la valeur saisie. 
# Depuis le dépôt, sur ta machine. Wrangler demande la valeur en secret.
cd apps/api
pnpm exec wrangler secret put SASPAY_API_KEY
pnpm exec wrangler secret put SASPAY_WEBHOOK_SECRET

Vérification sans exposer le secret : curl -s https://proofcore-api.laudesmassamba1.workers.dev/health. La réponse doit contenir "payments":{"provider":"saspay","configured":true}.

Deux limites SasPay à connaître. La spécification ne propose ni débit récurrent automatique ni remboursement par API : PROOFCORE fonctionne en périodes prépayées, renouvelées manuellement, et les remboursements restent administratifs. Les retraits exigent aussi l’IP du serveur en liste blanche, sinon l’API renvoie 403 ip_not_whitelisted.

Slack — alerte après paiement vérifié

Le workflow n8n est prêt ; il attend uniquement l’URL du canal.

Il te faut une URL Incoming Webhook Slack. Elle ressemble à https://hooks.slack.com/services/T…/B…/… et ne doit pas être publiée : toute personne qui la possède peut poster dans le canal choisi.

Comment l’obtenir

  1. Ouvre api.slack.com/apps et clique sur Create New App, puis From scratch.
  2. Nomme l’application PROOFCORE Alerts et choisis le workspace qui recevra les notifications.
  3. Dans le menu de gauche, ouvre Incoming Webhooks et active Activate Incoming Webhooks.
  4. Clique sur Add New Webhook to Workspace, choisis le canal (par exemple #proofcore-payments) puis autorise l’installation.
  5. Copie l’URL générée. Garde-la dans ton gestionnaire de secrets ; ne la mets ni dans Git, ni dans un ticket, ni dans le chat.
  6. Teste-la depuis ton terminal avec la variable déjà chargée : 
# Test visuel : un message doit apparaître dans le canal Slack.
curl -sS -X POST \
  -H 'Content-type: application/json' \
  --data '{"text":"PROOFCORE — test de notification"}' \
  "$SLACK_WEBHOOK_URL"
Droits nécessaires. Ton compte doit pouvoir installer une application dans le workspace. Si l’installation est réservée aux administrateurs Slack, demande-leur de créer le webhook ou de valider l’application.

n8n — une URL qui ne disparaît pas

Recommandé avant de compter sur les alertes en continu.

Le webhook public actuel utilise un Cloudflare Quick Tunnel. Son adresse est de la forme https://<nom-aléatoire>.trycloudflare.com/webhook/proofcore-payments et change à chaque redémarrage du tunnel ou de la machine. Le Worker pointerait alors vers une adresse morte.

Pour retrouver l’URL courante sans exposer de secret : docker logs proofcore-n8n-tunnel 2>&1 | grep -o 'https://[^ ]*trycloudflare.com' | tail -1

Option A — recommandée

Un sous-domaine que tu contrôles

Par exemple n8n.tondomaine.com. Fournis le domaine et l’accès DNS Cloudflare ; je configure un tunnel nommé et je mets à jour l’URL côté Worker.

Comment l’obtenir : achète un domaine chez un registrar, ajoute sa zone DNS à Cloudflare, puis crée le sous-domaine. Le tunnel n’exposera que le webhook, jamais l’éditeur n8n.

Option B — alternative

Un n8n hébergé avec URL stable

Fournis l’URL HTTPS du webhook et le moyen d’y configurer le secret partagé. Utile si tu ne veux pas maintenir un tunnel sur cette machine.

L’éditeur n8n peut rester privé : seule l’URL /webhook/… doit être joignable par le Worker.

Si tu ne fournis rien : les alertes fonctionnent tant que le tunnel tourne. Après un redémarrage, il faudra recréer le tunnel et remettre l’URL dans le secret Worker. Ce n’est pas une base fiable pour la production.

Console d’administration

Une simple adresse email, pas un secret.

La console /app/admin est désactivée tant que ADMIN_EMAILS est vide : l’API répond 503 admin_not_configured. Indique l’email du compte PROOFCORE qui doit voir les utilisateurs, abonnements, paiements, runs et webhooks. Plusieurs emails sont possibles, séparés par des virgules.

À fournir
L’email du compte administrateur

Ce n’est pas un mot de passe et ce n’est pas un secret. Il sera ajouté à ADMIN_EMAILS dans apps/api/wrangler.toml, puis le Worker sera redéployé.

Remise sécurisée

Comment me transmettre les accès sans les exposer.

À faire

  • Utiliser un gestionnaire de secrets (1Password, Bitwarden, Vault…).
  • Pour SasPay, lancer toi-même wrangler secret put : la valeur reste hors de l’historique du shell.
  • Pour Slack, conserver l’URL dans le gestionnaire et me prévenir quand elle est prête.
  • Faire les tests avec la clé sk_test_… avant toute clé sk_live_….

À ne pas faire

  • Coller une clé, un secret ou le mot de passe QA dans le chat.
  • Committer un fichier .env ou un PDF contenant des secrets.
  • Mettre la clé SasPay dans le frontend, un log ou un rapport.
  • Utiliser la clé LIVE avant d’avoir vérifié un paiement test de bout en bout.
Ce que je vérifie sans voir les secrets : le fournisseur actif dans /health, la réception d’un webhook signé, l’exécution du workflow n8n et l’arrivée du message dans Slack. Les secrets restent dans les stockages prévus.

Checklist finale

À cocher au fur et à mesure. Une case ne se coche qu’après vérification réelle, pas après simple lecture du code ou d’un dashboard.

  • Compte SasPay créé, email vérifié et KYC validé.
  • Clé sk_test_… créée et copiée dans le gestionnaire de secrets.
  • Webhook SasPay créé vers /api/webhooks/saspay, abonné à transaction.success, signing secret copié.
  • Paiement sandbox vérifié : SUCCESS, accès activé seulement après vérification serveur.
  • Clé sk_live_… créée après le test.
  • Application Slack installée, URL Incoming Webhook copiée, message de test reçu.
  • URL n8n stable fournie, ou décision assumée de garder le Quick Tunnel temporaire.
  • Email admin fourni pour ADMIN_EMAILS.
  • Aucun secret dans Git, le chat, les logs ou le frontend.
Après réception : je configure les secrets, je vérifie le fournisseur, je fais un paiement test, je contrôle la notification Slack et l’exécution n8n, puis je passe seulement ensuite à la clé LIVE. Les étapes seront validées une par une, pas déclarées actives sur simple lecture du code.
