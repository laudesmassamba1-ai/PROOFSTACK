# Audit de sécurité PROOFCORE — 21 novembre 2026

Périmètre : API (`apps/api`), application web (`apps/web`), CLI et pont local
(`packages/cli`), configuration de déploiement (Cloudflare, Vercel). Méthode : revue du
code et des surfaces exposées, puis trois lectures complémentaires.

1. **Utilisateur lambda** — inscription, connexion, mot de passe oublié, support,
   partage de projet, export. Objectif : obtenir un accès ou une donnée sans droit.
2. **Attaquant** — vol de session, CSRF/CORS, IDOR, escalade de rôle, injection,
   SSRF, contournement de webhook, force brute, épuisement mémoire.
3. **Informaticien** — preuves `fichier:ligne`, invariants, chemins d'exécution,
   contrôles réellement appliqués, ce qui reste une limite assumée.

Aucun test n'a été simulé par un faux succès : un contrôle absent est décrit comme
absent, pas comme « à vérifier ».

---

## Constats corrigés dans cette passe

### A1 — Escalade opérateur par le domaine `@proofcore.dev` — CRITIQUE

**Preuve.** `apps/api/src/routes/account.ts` (avant correction) :

```ts
const isOperator =
  found.user.email === services.config.supportEmail ||
  found.user.email.endsWith("@proofcore.dev");
if (!isOperator && !isAdmin(services, found.user.email)) { ... }
```

**Scénario.** N'importe qui s'inscrit avec `ceo@proofcore.dev`. L'adresse n'est pas
vérifiée, mais `GET /api/account/delivery-status` le traite comme opérateur et renvoie
les 25 derniers messages de l'outbox. Un lien de réinitialisation suffit ensuite à
prendre le compte visé. La console `/outbox/:id` était déjà protégée par la liste
explicite : deux règles contradictoires pour la même surface.

**Correctif.** Seule la liste `ADMIN_EMAILS` accorde le statut. Le domaine et
`supportEmail` ne sont plus des preuves d'identité. Test de non-régression :
`apps/api/test/account.test.ts`, « does not grant delivery status to a
self-registered @proofcore.dev address » (403), et l'admin explicite reste à 200.

### A2 — Upload de run sans limite de taille — HAUTE (déni de service)

**Preuve.** `apps/api/src/routes/machine.ts` lisait `await c.req.json()` avant toute
validation. Une clé `runs:write` pouvait envoyer un corps arbitrairement grand ; le
Worker le chargeait entièrement en mémoire avant que Zod ne le rejette.

**Correctif.** Le même lecteur que les routes web (`readBody`) applique d'abord
`Content-Length`, puis la taille sérialisée, avant la validation du contrat de run.
Un corps trop grand répond `413 payload_too_large`. Les autres routes JSON étaient
déjà couvertes ; les webhooks ont reçu le même contrôle après lecture, car
`Content-Length` est absent sur une requête chunked.

### A3 — SSRF des outils IA et des fournisseurs — HAUTE

**Preuves.**

- `apps/api/src/routes/ai.ts` : `fetchFrom` utilisait `redirect: "follow"`. Une URL
  publique qui redirige vers `169.254.169.254` contournait `assertPublicUrl`.
- `resolveProvider` acceptait `http://127.0.0.1:...` comme base d'un fournisseur
  « custom ». Le serveur y envoyait ensuite la clé et la conversation.
- `fail_scan` vérifiait l'appartenance au workspace avec un `||` entre protocole et
  hôte : un projet de base `http` autorisait n'importe quel hôte `http`.

**Correctifs.**

- redirections suivies manuellement, chaque saut revalidé, cinq sauts maximum ;
- corps distant plafonné à 2 Mo, au lieu de `response.text()` sans borne ;
- base fournisseur obligatoirement HTTPS, hôte public (loopback, link-local,
  `.internal`, `.local`, IPv6 privées refusés) ; redirections fournisseur refusées.
  Seul le lanceur de tests (`VITEST`/`NODE_ENV=test`) peut joindre son faux fournisseur
  local ; un Worker déployé ne remplit jamais cette condition ;
- appartenance au workspace : égalité d'hôte obligatoire, sans disjonction.

**Limite résiduelle.** Le contrôle ne résout pas le DNS : une attaque par rebinding
reste théoriquement possible si l'hôte public bascule vers une IP privée entre la
validation et la connexion. La parade complète est un proxy de sortie avec résolution
et épinglage d'IP ; elle n'est pas en place.

## Contrôles vérifiés comme solides

| Surface          | Contrôle observé                                                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Sessions         | cookie `ps_session` `HttpOnly`, `SameSite=Lax`, `Secure` en production ; jeton stocké haché ; expiration vérifiée à chaque requête             |
| Réinitialisation | jeton 32 octets à usage unique, TTL 1 h ; `updateUserPassword` sans `keepSessionId` supprime **toutes** les sessions ; test existant le couvre |
| CSRF             | garde `Origin` sur toutes les écritures `/api/*` hors webhooks ; origine inconnue → 403 ; préflight CORS limité à `WEB_ORIGIN`                 |
| IDOR             | projets, runs, rapports et sessions filtrés par workspace ou propriétaire ; ressource étrangère → 404, jamais 403                              |
| Clés machine     | Bearer `psk_` haché, scopes vérifiés, workspace et projet imposés par la clé, `Idempotency-Key` requis                                         |
| Webhooks         | signature sur le corps brut, fenêtre de 300 s, event id unique, vérification serveur du paiement ; payload plafonné                            |
| XSS              | aucun `dangerouslySetInnerHTML` ; React échappe noms, sujets et réponses support ; CSP `script-src 'self'` sur Pages et Vercel                 |
| SQL              | requêtes paramétrées ; les rares noms de table interpolés sont des constantes internes                                                         |
| En-têtes         | HSTS, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` sur les deux déploiements                                   |
| Secrets          | clés lues à l'exécution depuis l'environnement ; clé IA chiffrée ; aucune clé dans le frontend ou le dépôt                                     |

## Risques résiduels, classés

1. **Corrigé — sessions de 30 jours sans rotation.** Le TTL est passé à **7 jours** ;
   un changement/reset de mot de passe révoque toutes les autres sessions. Un cookie
   volé reste valable au plus 7 jours, sans rotation glissante (compromis assumé pour
   éviter une écriture D1 et un `Set-Cookie` à chaque requête).
2. **Moyen — PBKDF2 à 100 000 itérations.** Sous la recommandation OWASP actuelle pour
   SHA-256. Le runtime Workers rejette toute valeur supérieure à 100 000 : la corriger
   exige un autre KDF (ou un service dédié), pas un simple changement de constante.
   Aucun contournement n'a été inventé.
3. **Faible — limiteurs en mémoire par isolate.** Les limites de connexion, mot de
   passe et recherche support ont un backstop D1 ; les autres surfaces (scan, device,
   IA) retombent sur la limite de l'isolate, doublée des quotas de plan en base. Un
   attaquant distribué peut les dépasser ; la parade est une règle de rate limiting
   Cloudflare ou un compteur D1 par surface.
4. **Corrigé — `support/:reference` public.** Limiteur durable D1 de 30 recherches par
   adresse et par heure, en plus de la référence de ~80 bits et de l'e-mail exigé.
5. **Corrigé — `ADMIN_EMAILS` n'est plus dans `wrangler.toml`.** Il est posé comme secret
   Worker ; le dépôt ne publie plus l'adresse de l'opérateur.
6. **Faible — pas de vérification d'e-mail obligatoire** avant l'usage normal. Elle
   n'accorde plus de privilège (A1), mais elle permettrait encore l'inscription avec une
   adresse usurpée.
